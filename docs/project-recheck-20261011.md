# 修复后项目复查（2026-10-11）

结论：主要功能和上一轮防护已经存在，但开户、金额精度、删除关联仍未形成完整闭环。此次只分析并使用临时 SQLite 复现，不修改业务代码，不连接生产服务。

## 已确认的剩余问题

1. **P1 开户绕过账务和关系校验**：`main_from_txt.py:5673` 直接用 MemberCreate 创建 Member。临时库以管理员 POST 创建会员，coin=100、freeze_coin=20、parent_id=999999，返回 201；实际存入上述值，金币流水为 0。不存在的上级可进入旧表，后续 enrollment 会继承。建议开户余额和冻结余额固定为零，初始资金走专用调账；邀请关系统一由经过校验的绑定流程建立。
2. **P1 调账范围与存储精度不匹配**：`member_policy.py:264` 允许 24 位、6 位小数，最终却转换 float 存储。临时库提交 999999999999999999.123456 返回 200，实际余额为 1e18。不是只有显示格式问题，落库金额已变化。迁移前至少限制业务上限，并验证持久化前后六位小数一致；长期统一 Numeric 或整数最小单位，覆盖余额、冻结、流水及结算全部路径。
3. **P1 删除关联仍有遗漏**：`main_from_txt.py:5812` 未检查 AlipayAccount、AppRefreshSession、WechatIdentity 等关联。临时库构造只有支付宝绑定的会员，删除返回 204，支付宝记录仍存在。该复现说明遗留数据路径风险，不代表标准 APP 登录流程必然可触发；正常流程中的其他关联可能先阻止删除。建议业务会员只停用，硬删除覆盖所有模块外键和关联。
4. **P2 APP 状态恢复仍不完整**：业务 ViewModel 生命周期已改善，但 SubsidyForm 的姓名/账号/金额仍是 remember，旋转可丢失输入；补贴幂等键仍在内存，进程死亡会丢失。应持久化待确认提交键及非敏感草稿，恢复时先查结果。
5. **P2 生产验收不足**：PostgreSQL 跨游戏短信咨询锁尚无真实并发验证；Docker 已配置挂载，但未验证旧附件迁移和重建持久性。短信、微信、广告和支付仍需真实服务验收。
6. **交付风险**：APP、策略模块、迁移和部分测试仍为未跟踪文件。凭据文件已忽略，但尚需整理可复现的版本提交；不要直接使用 git add . 收集工作区中的截图、备份及辅助文件。
