# 项目检查（2026-10-11）

## 结论

项目具备广告会员运营后台和 Android APP 的主要业务链路，包含登录、风控、广告可信回调、奖励、代理分佣、提现和补贴。但生产初始化、余额修改入口和新旧会员数据整合存在已确认缺口，当前不应认定为完整生产验收通过。本次仅分析和临时数据库验证，未修改业务代码或生产数据。

## 结构

- FastAPI / SQLAlchemy 后台，主要逻辑集中在约 6200 行的 `backend/app/main_from_txt.py`；`main.py` 是导出入口。
- 专项模块：`payouts.py`、`payment.py`、`device_risk.py`、`member_policy.py`、`sms_auth.py`、`taku_ecpm.py`。
- `public/` 原生 JavaScript 管理界面；`server.js` 提供本地静态服务及后端代理。
- `apk/test_android/` Kotlin / Compose APP，接入微信、阿里云设备 SDK、广告和会员接口。
- Alembic 数据迁移，目标生产数据库 PostgreSQL；当前自动回归主要用临时 SQLite。

## 已确认问题（按优先级）

1. **P0：生产启动额外创建硬编码弱密码超级管理员。** `main_from_txt.py:2317` 不检查生产环境，lifespan 每次调用 seed_data。临时库把 APP_ENV 设为 production 并运行 seed_data 后，实际得到两个管理员，其中一个为环境变量指定账号之外的超级管理员。报告不复述凭据。应移除默认附加账户创建，并核查已部署库中的该账号及历史操作；仅修改代码不会注销已有账号或令牌。生产空库还会进入演示业务数据初始化。
2. **P1：通用会员编辑可直接改余额，绕过账务入口。** `MemberUpdate.coin/freeze_coin` 可由 operator 通过 `update_member` 直接赋值；该路径没有会员行锁和 CoinLog。临时库 PATCH coin=100 返回 200，余额变为 100，金币流水为 0。与广告和提现并发时存在覆盖余额风险。应禁止通用资料接口改资金，统一使用带权限、锁、流水和审计的调账事务。
3. **P1：新旧邀请关系不一致。** `update_member` 修改 Member.parent_id，不同步 Enrollment.parent_id，也未在该入口执行新邀请关系校验。复现 PATCH parent_id=0 后，Member 为 0，而 Enrollment 仍为 2，后台旧查询和新分佣算法会读取不同上级。应统一关系来源，限制改绑，并明确在途广告快照行为。
4. **P1：删除会员未覆盖新增关联。** `delete_member` 关联检查遗漏 Enrollment、下级邀请关系、RewardLedger 等新模块数据。临时库删除有直属下级的邀请会员返回 204，Enrollment 仍存在。应阻止有关联会员硬删除或采取停用策略，并补齐新模块关联检查。
5. **P1：Compose 部署配置不完整。** sms_auth 从环境读取四个 SMS_ALIYUN 配置，但 compose 未透传，也未使用 env_file；仅填 .env 不能使其自动进入容器。应用服务未挂载上传目录，头像和补贴图片写入容器可写层，重建容器可能丢失。支付宝密钥仅提供路径变量，未配置密钥文件挂载。需补齐部署契约并验证容器重建后的附件读取。
6. **P2：资金精度未统一。** 分佣流水使用 Numeric(24,6)，会员余额、冻结余额和 CoinLog 仍使用 Float；需要统一 Decimal/定点精度并迁移对账，不能只修改新分佣表。
7. **P2：短信限流跨游戏并发边界。** 限流按手机号/IP 全局查询，但锁为单游戏行；PostgreSQL 中不同游戏请求可同时通过全局配额检查。应使用手机号/IP 维度原子配额或锁，并补 PostgreSQL 并发测试。
8. **P2：APP 页面状态恢复边界。** 会员中心在 Compose 页面内部创建 ViewModelStore，离开组合时清理，旋转或重新进入会丢失部分表单及补贴申请内存状态。提现已有独立幂等恢复保护，但不能推断所有提交路径同样完善。
9. **交付管理：** APP 目录、新策略/短信模块和迁移仍有未跟踪文件，不能仅推送已跟踪文件完成部署。serverdata.md 当前未被 Git 跟踪，也未被 .gitignore 排除，应排除含凭据文件后再整理提交。未读取或复述其内容。
