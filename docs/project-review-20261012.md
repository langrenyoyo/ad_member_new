## 本次发现

### 1. 高优先级：整笔分佣缺失不能被对账发现（已复现）

后续修复：新结算的主奖励台账快照增加 `commission_audit_version=1` 和 `commission_outcomes`，保存候选上级、对应等级、资格结果、应发金额及跳过原因。对账从应发结果反查分佣台账，即使分佣台账、流水及余额变化同时丢失，也能报告 `expected_commission_missing`。没有历史资格结果的旧快照继续沿用保守检查，不能把兼容通过解释为历史分佣完整性已证明。此记录与奖励入账同事务；不产生额外分佣、不自动补款。

位置：`backend/app/wallet_audit.py:70`、`:105`；实际分佣计算在 `backend/app/member_policy.py:515`。

对账从已有 RewardLedger 检查入账，又检查孤立的 301 流水，但没有从广告结算的预期分佣反向检查完整性。

临时 SQLite 中调用真实 settle：奖励 10 金币，合格上级应获 1 金币；正常结算对账通过。随后模拟整笔漏记，移除该分佣台账及入账流水、恢复上级原余额，对账仍返回 `passed=true`、`findings=[]`。这是对账检测缺口，不是已经证明正常回调会漏发分佣。

建议：持久化每个候选受益人在结算时的应发金额、实际资格判断及跳过原因，再反向核验应发与实发。不能只依据请求时 recipients 判缺失，因为现有 settle 会在回调时再次检查等级、状态和游戏归属，部分跳过属于现行规则。

### 2. 中优先级：异常快照会中断整个对账（已复现）

后续修复：已显式校验快照为对象，将数组、null、数字、字符串、损坏 JSON 和非法 rule 记录为 invalid_settlement_snapshot，继续检查其他钱包记录。资金专项 8 项通过。整笔分佣缺失的检测缺口仍未修复，不受此结构校验修复覆盖。

位置：`backend/app/wallet_audit.py:113`。

策略快照 result_json 为合法 JSON 数组 `[]` 时，解析后调用 `.get()` 抛出 AttributeError，现有异常分支仅处理 ValueError/TypeError。临时库已复现，对账无法继续输出其余记录的问题。正常写入生成对象，本项主要影响历史异常数据或修复后的检查。

建议：显式校验快照为对象，将结构异常记录为 invalid_settlement_snapshot，继续检查其他记录。

### 3. 中优先级：补贴提交和恢复未共享完整互斥范围（静态确认，未做真机复现）

位置：`apk/test_android/app/src/main/java/com/example/idiomquiz/ui/MemberCenterViewModel.kt:162`、`:202`；重试按钮在 `MemberCenterScreen.kt:25`。

recoverCampaign 使用 recoveryMutex，但 applySubsidy 创建、发送和清除待确认记录未持有同一把锁。重试按钮仅检查 recovering，不检查 busy，且恢复提示在成功后仍保留。

可能时序：提交 A 后同时点击恢复；提交 A 先完成并清除 pending，用户发起 B；较慢的 A 恢复请求随后返回，仍执行无条件清除 pending，导致 B 的本地恢复记录丢失。session epoch 只隔离登录会话，不能区分同一会话的 A/B 请求。服务端幂等可以减少 A 重复申请，无法保护 B 的本地恢复记录。

建议：新提交和恢复共享请求互斥范围，清除时比较 request_key；同时收敛按钮状态。用可控延迟的请求模拟覆盖上述时序。
