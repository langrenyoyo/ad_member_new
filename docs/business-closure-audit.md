## 已确认的缺口

### 高优先级：旧设备封禁未阻止已登录用户申请广告

位置：`backend/app/main_from_txt.py` 的 `require_app_member`（2587 行）、`app_ad_request`（2888 行）。

专项复现：临时数据库、production 环境、TAKU 配置有效（仅模拟凭据，不请求渠道），创建会员登录 token；将该会员 `MemberDevice.device_id_ban` 和 `imei_id_ban` 都设为 1，用同一客户端设备 ID 和原 token 请求广告，返回 HTTP 201。

影响：后台旧设备“封禁”设置不能作为广告准入拦截依据。新阿里云设备风控的每日限次是另一套规则，不能代替旧封禁。修复需统一明确设备封禁语义并接入服务端准入，测试已有 token、原设备、换设备、解除封禁等场景。

### 中优先级：广告冷却配置没有在申请入口执行

位置：同上 `app_ad_request`；`game_ad_config` 返回配置但申请流程未按冷却时间检查。

专项复现：临时数据库配置 TAKU rewarded 的 `cooldown_seconds=3600`，bootstrap 确认返回 3600；立即使用两个不同 `client_request_id` 连续申请广告，两次均返回 HTTP 201。

影响：客户端可跳过冷却，不应将前端倒计时当作服务端频控。新设备风险每日限次不等于正常用户冷却限制。修复需明确按申请、展示或完成计时，并允许同一请求的幂等重试。

### 补贴只完成审核闭环，未完成补贴资金到账闭环

位置：`backend/app/main_from_txt.py` 的 `approve_subsidy`（5895 行）；`backend/tests/test_app_subsidies.py` 的 `test_apply_admin_review_and_app_result`。

现状：APP 申请 → 后台审核 → APP 查看结果可用。审核通过仅更新状态与审核信息。测试明确验证审核后余额不变、未新增金币流水；没有由此自动创建支付宝补贴转账订单。

如果产品要求审核通过后支付补贴，则还缺发放方式、资金订单、幂等入账、失败补偿和 APP 到账状态。不能将“审核通过”向用户展示为“已到账”。

## 依赖外部验证的环节

- TAKU：模拟验签回调、重复与并发回调、防重复奖励、客户端完成等待回调等测试通过。本次未验证线上最新回调或真实奖励，不能沿用旧服务器记录推断当前状态。
- 支付宝：申请冻结、驳回/确认失败退回、成功清冻结、超时查单等测试通过。真实应用权限、密钥、通知及实际到账仍需联调。
- 提现自动任务：已有 `scripts/reconcile_alipay.py`，但仓库部署配置没有自动安装调度。批量定时转账需要运行带 `--execute` 的任务；只入队而没有执行器不能自动到账。生产调度是否已安装本次未核查。
- 阿里云：当前仅使用模拟云响应验证同设备关联、限次和异常拦截；真实设备标识、bizId 绑定及重装行为仍需真机验证。它是疑似清数据/重装识别，不能承诺百分之百识别恢复出厂。
- 用户认证：这次业务专项多数用测试直接签发 token，不能把这些测试等同于从实际 Android 注册、登录、刷新到提现的连续端到端验收。
- 数据库：本次验证 SQLite；没有执行 PostgreSQL 并发测试。

## 验收建议

1. 先修复设备封禁和冷却的服务端拦截，并增加回归用例。
2. 若补贴包含付款，补齐支付/入账状态闭环。
3. 配置并验证提现执行器与查单调度，包括服务重启后的处理中订单恢复。
4. 在测试账号上走一次真实 Android 登录 → 云端设备识别 → 广告展示 → TAKU 回调 → 钱包流水 → 小额支付宝提现到账流程，逐步核对订单号、流水和余额。
