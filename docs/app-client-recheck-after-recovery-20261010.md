# 引导恢复修复后的 APP 复查

结论：上轮修复已经落入代码，但仍存在异常路径缺口，尚不能认定已完善。本轮仅静态检查和读取已有测试结果，没有改业务代码或重新构建；ADB 无设备。

## 已确认修复

- 强制支付宝引导页已提供手机号短信验证设密，并由后端校验验证码归属于当前会员。
- 已加载规则时普通网络错误不再直接全屏阻断；前台刷新任务位于引导分支之前，不随引导显示消失。
- RESUMED 时检查使用权限并刷新，暂停时取消定期刷新 Job。
- DEVICE_COOLDOWN 页面有钱包入口和服务端恢复时间。
- 引导内普通表单按用户 rememberSaveable，密码和验证码仍只保存在内存。

## 仍需修复

1. **P1：业务 401 被自动重试。** `AuthRepository.kt:68` 的认证请求对任何 401 刷新并重试。短信设密接口 `sms_auth.py:84` 会将错误验证码计数后返回 401，因此一次错误提交可能计两次，5 次上限可能在第 3 次提交触发。需要业务错误码与 Token 过期分离；不要自动重放验证码消费操作。
2. **P1：初始化与自动刷新未串行协调。** 登录成功主动调用 initializeApp，同时 currentUser 改变触发 Compose RESUMED 刷新。initializeApp 不受 onboardingBusy/共同互斥锁保护，还会再次 loadOnboarding；旧请求与新请求可能覆盖门禁状态。应统一初始化/规则刷新入口，增加操作代次，合并同时发生的请求。
3. **P1：冷却期重启或凭据过期后恢复入口仍不可用。** restoreSession 对 /me 的 403 清除会话；刷新 Token 的 403 也清除凭据。冷却状态会触发这些路径，钱包的恢复例外只能在当前有效会话下工作。需要后台受限恢复认证方案与 APP 登录状态区分，不能简单放行全部冷却期登录。
4. **P2：权限采集取消与刚启用策略的状态不完整。** loadOnboarding 在 GET 成功后，直到统计上传成功才写入新策略；若后台刚启用 require_usage，而采集或上传失败，APP 仍保留旧策略，可能继续本地功能（服务端仍会拒绝业务请求）。暂停只取消定时刷新 Job，不覆盖登录初始化/绑定邀请触发的加载；AppUsageCollector 的同步事件遍历没有协作取消检查。应先应用新策略，再单独处理统计同步状态，并统一任务作用域。
5. **P2：普通微信登录仍无超时。** 设密有超时，loginWithWeChat 只有立即失败或 SDK 事件才能清 authBusy；回调丢失会卡住登录按钮。
6. **P2：短信交互仍混用密码登录规则。** 验证码登录共用下方密码框作为新密码，缺少独立模式和确认；401/422 仍被通用 readableError 映射为密码错误。冷却期点击发送直接 return，用户看不到剩余秒数。
7. **P2：跨步骤会话隔离未完全覆盖。** 广告的 epoch 在异步获取云 Token 后才捕获；初始化也没有贯穿全流程的共同 epoch。原会话在 SDK 等待期间变更时，后续步骤可能用新账号请求旧上下文，虽通常由后台拒绝，仍可能干扰界面状态。
8. **P2：会员中心重建与真机覆盖不足。** 自建 ViewModelStore 退出页面即清理，补贴凭据/幂等状态仍不耐重建；缺少 Compose 导航、弱网、微信回调、撤权、进程重启以及冷却期恢复的设备测试。

## 验证边界

已有最新结果为 Android 26 项 JVM 测试全部通过，Lint 无错误、92 警告、2 提示。新增 3 项测试覆盖门禁判定函数，没有覆盖完整页面生命周期或网络并发。现阶段适合继续集成测试，不宜据此宣布正式上线验收完成。

建议顺序：先修复业务 401 重放和初始化并发，再设计冷却期受限恢复会话，随后补权限同步及微信/短信交互，最后真机验证。
