## 已复现的对账缺陷

### 1. 同一交易的后补证明无法更新待核验状态

- 位置：`backend/app/main_from_txt.py:3446`，查询已处理 `taku:<trans_id hash>` 后直接返回 200。
- 触发：SDK 已发奖，第一次 S2S 回调未带 eCPM 字段，保存 `taku_reconciliation`，状态为 `ecpm_missing_or_invalid`；随后同一交易带有效证明重试。
- 临时库复现：两次均返回 200，但 `callback_ecpm_verified` 仍为 false，`callback_ecpm` 仍为空。
- 影响：目前的幂等逻辑保护了钱包，却也阻止对账补全；“后续平台补字段即可自动转为已核验”不成立。
- 建议：将发奖幂等与证明更新分开；已完成发奖不可重复入账，但同一交易经过验签及绑定后应允许补全有效证明，并保留审计轨迹。

### 2. 无有效 eCPM 证明的回调覆盖结算价字段

- 位置：`backend/app/main_from_txt.py:3510` 附近，`record.ecpm`、`record.settlement_ecpm` 赋值为由 `reward_amount` 转出的数值。
- 临时库复现：SDK 可信人民币 eCPM 为 200；回调不含证明、`reward_amount=2000` 后，`ecpm` 与 `settlement_ecpm` 由 200 变为 2000，`callback_ecpm` 仍为空。
- 影响：会员钱包未变化，但广告列表、导出以及提现附带的结算价可能展示错误口径。D+1/D+2 本地预估使用 shown 元数据，不直接使用这个被覆盖字段，不能把此缺陷扩大为所有报表金额都错误。
- 建议：分别保存奖励数量、客户端可信价、平台回调可信价和实际发奖结算依据；缺少有效证明时保留原结算依据，不将 `reward_amount` 当作已验证 eCPM。

以上两项已在临时 SQLite 数据库复现，未修改线上业务数据。复现脚本与日志在 `artifacts/requirements-audit-20261028-repro.py`、`artifacts/requirements-audit-20261028-repro.log`。

## 两种核验不能互相替代

- 单次 S2S eCPM 核验：平台回调验签、广告会话绑定、交易去重、密文解密与来源校验。用于单笔广告核验。
- D+1/D+2 收益核检：通过设备报表 API 拉取同应用、用户、广告位、日期、币种的数据，对比本地 shown 收益预估。提现需求中的差异额/差异率来自这套流程，不是直接从 `s_id/e_c/e_c_cny` 查询。
- 目前只能确认本轮会话没有 S2S 的这三个字段，不能据此推断所有历史回调都不存在。此前对话中“该笔已返回这些字段”的说法已被按交易匹配的核查结果纠正。
- 当前 `/complete` 实现要求 SDK 上报有效人民币加密证明，并调用奖励策略计算。不能再用早期文档中的“纯固定金额、无需 eCPM 证明”概括当前实现。
- S2S 返回 200 不等于 eCPM 已核验；定时任务退出成功也不等于有可用报表。
