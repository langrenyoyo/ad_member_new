# 最新复查：恢复逻辑与对账边界

本轮检查当前源码并在临时 SQLite 数据库复现问题。未保留业务代码修改，未部署或操作生产数据。

## 结论

ECPM 准入预检、奖励后曝光补报、标签统计和基础 Decimal 资金链路已落地；自动识别、生产副本验收尚未完成。本轮发现以下需要继续修复的边界。

### P1：资金对账存在假通过

位置：`backend/app/wallet_audit.py:11`。

对账只遍历现存 Member，再查询对应 CoinLog 和 Payout。孤立的金币流水、没有会员的提现及提现关联缺失未被扫描。

临时库插入 user_id=99999 的错误流水（0 + 1 != 2），以及 member_id=99999、withdrawal_id=99999 的待审核提现；该会员及提现主记录均不存在。实际返回 findings=[]、passed=True。

建议增加全表反关联检查，覆盖孤立流水、提现关联、奖励/分佣台账与入账流水的一致性，并检查未知提现状态。不能仅凭当前 passed 字段认定迁移对账完成。

### P1：补贴恢复失败阻断其他会员功能

位置：`MemberCenterViewModel.kt:59`、`:185`。

每次 load 都先执行 recoverCampaign，恢复请求的网络错误或 5xx 会抛到 runAction，导致后面的会员资料、金币流水、提现记录、密码页等加载不执行。待恢复申请保留，下次切页又先触发同一失败。

这是代码路径确认，尚未进行真机断网复现。建议恢复任务独立运行、可见提示及手动重试；非关联页面应继续加载。保持原幂等键，不能用删除未确认请求规避错误。

### P2：损坏 ECPM 配置阻断后台止损操作

位置：`backend/app/member_policy.py:235`、`:258`；`backend/app/taku_ecpm.py:63`。

保存任何策略都调用密钥检查，即使 reward_enabled=False，仍读取和验证 keyring。临时库将环境变量指向不存在的文件，提交关闭奖励并修改公告，返回 503。

建议拆分“广告准入是否可用”与“管理变更是否允许”：启用依赖可信证明的奖励时强校验，关闭奖励及无关公告/风控修改不应依赖损坏的广告密钥。广告准入仍应保持失败关闭，避免绕过已配置的证明校验。

### P2：曝光恢复串行阻塞初始化和钱包

位置：`AuthRepository.kt:130`、`:146`、`:210`。

initializeApp 和 walletBalance 都等待 retryImpressions；最多 20 条逐条网络请求，没有批次总时限。慢网下，补报会显著延后用户所需的初始化或余额刷新。当前只有固定事件 ID 和持久化队列，尚无独立调度、退避及队列性能测试。

建议将补报从关键读取路径移出，增加单消费者、退避及总预算；保留会话 epoch 和退出清理。补报失败不应使钱包无法及时读取。
