# 《快手风控python.txt》接入评估

## 结论

这份脚本**不适合直接介入当前项目生产链路**，可以作为“离线运营预警模型”的原型参考，经过数据定义、公式修正、历史回测和人工审核后，才适合接入后台风控辅助模块。

它当前不能完成以下工作：

- 不能调用快手官方接口或自动拉取联盟数据；
- 不能从本项目数据库自动计算五项指标；
- 不能识别具体用户、主体、游戏、广告位或设备；
- 不能给用户 APP 提供广告请求、展示验证或奖励结算；
- 不能安全地自动执行“暂停首充”“缩减流量”等整改动作。

本项目当前是管理后台，已有会员、广告历史、设备和风控历史模型，但没有用户 APP 专用认证与广告会话接口。该脚本最多应作为后台的“主体/游戏级风险评分输入”，不能作为用户级封禁或广告奖励依据。

## 1. 文件本身的问题

### 1.1 文件不是可执行的 Python 脚本

文件把说明文字、`python` 标记和代码粘在 TXT 中。所谓代码行以 `#` 开头，后面的 `def calc_risk_score`、`get_warn_level` 和主程序都在同一行注释中。将该行单独编译时 Python AST 的语句数量为 `0`，因此“编译通过”并不代表脚本可运行；执行 TXT 文件也不会得到风险结果。

### 1.2 它不是 AI 模型

实现意图是固定权重规则：35 + 25 + 20 + 12 + 8。没有训练数据、特征版本、模型评估、阈值回测、置信度或漂移监控。名称中的“AI”不能作为接入决策依据。

### 1.3 指标定义不完整

| 指标 | 文件定义 | 当前项目是否直接存在 | 主要问题 |
|---|---|---:|---|
| `pay_rate` | 充值转化率，百分比 | 否 | 项目没有充值订单/支付转化事实表，无法计算分母和统计窗口 |
| `retain_1` | 次日留存，小数 | 否 | 有会员创建时间和登录日志，但需要定义注册 cohort、有效登录和时区 |
| `ctr` | 广告点击率，百分比 | 否 | 有广告历史和抽奖记录，但没有曝光/点击事件的完整链路 |
| `flow_growth` | 流量环比涨幅，百分比 | 部分可推导 | `daily_activity.num` 可作为候选流量，但需确定是请求、展示、点击还是用户数 |
| `device_repeat` | 设备重复占比，小数 | 部分可推导 | 有 `member_devices`、会员设备字段，但没有快手设备指纹口径和去重规则 |

当前相关模型是：`AdRecord`、`LotteryRecord`、`MemberLoginLog`、`MemberDevice`、`RiskRecord`、`DailyActivity`、`CoinLog`。它们可以提供部分原始数据，但不等于已经具备五项指标。

## 2. 评分公式审查

### 2.1 设备重复项会直接冲破权重

文件注释说设备重复占比权重为 8 分，输入示例为 `0.13`。但公式写成：

```python
score += device_repeat * 8 * 100
```

`0.13` 会贡献 `104` 分，单项就超过总分，最终几乎必然被截断为 100。若输入是小数，至少应改为 `device_repeat * 8`；若输入是百分数，才应先除以 100。输入单位必须统一并校验。

### 2.2 留存项没有单项截断

```python
(1 - retain_1 / 0.35) * 25
```

当留存大于 35% 时会产生负分，当留存为负数或超过 1 时也没有校验。应先限制输入范围，再将该项限制在 `[0, 25]`，并明确“高留存是降低风险还是仅代表健康度”。

### 2.3 风险方向没有业务证据

- 付费转化率越高，当前公式风险分越高；这可能是想识别异常流量，也可能与正常经营指标相反。
- 流量环比增长越高，风险分越高；负增长会贡献负分。
- CTR 使用相对 3.5% 的绝对偏差，过低和过高都会增加风险。

这些方向不能只靠变量名确定，必须使用历史处罚、拒付、异常流量或人工标注数据验证。

### 2.4 输入没有范围和单位校验

至少应校验：

- `pay_rate`、`ctr`、`flow_growth` 的百分比范围；
- `retain_1`、`device_repeat` 是否为 `[0, 1]` 小数；
- 空值、负数、NaN、无穷大；
- 统计窗口、主体/游戏维度和数据来源。

### 2.5 样例数据会得到高危

按文件样例计算，设备项本身已经贡献 104 分，最终分数被截断为 100，输出“高危”。这个结果由单位错误主导，不能用于验证模型有效性。

## 3. 与当前项目的适配度

### 可复用部分

1. `RiskRecord` 已有 `risk_score`、`risk_level`、`action`、`tags`，可以承载评分结果和审计记录。
2. `MemberDevice` 已有设备 ID、IMEI、root、USB 调试、封禁标志和点击计数，可作为设备风险原始数据的一部分。
3. `AdRecord`、`LotteryRecord`、`MemberLoginLog` 和 `DailyActivity` 可作为广告、活跃和流量分析的候选数据源。
4. 后台已有 `/api/v1/risk/history`，可扩展为查看模型评分历史。

### 不能直接复用的部分

1. 当前 `/api/v1/risk/devices` 明确返回 `503`，因为设备风控数据源和入选规则尚未确认。
2. 当前广告数据主要是运营明细/导入数据，缺少可验证的广告请求、曝光、点击、完成和 provider 回调事件。
3. 当前数据库没有充值订单和支付转化模型，`pay_rate` 没有可靠来源。
4. 当前数据库没有留存 cohort 汇总表，`retain_1` 需要从注册和登录事件重新定义计算。
5. 当前 API 使用管理员 Bearer 鉴权；不能把该脚本直接放入用户 APP 广告链路。
6. 当前模型没有评分版本、输入快照、计算时间、窗口、阈值版本和人工复核结果，无法审计同一主体为何得到某个分数。

## 4. 推荐接入边界

建议把它定位为：

```text
原始事件/外部报表
    -> 日级指标聚合
    -> 版本化风险规则评分
    -> RiskRecord 预警记录
    -> 管理后台人工复核
    -> 经过授权后执行运营动作
```

不建议的链路是：

```text
APP 上报几个数字 -> 直接算分 -> 自动扣金币/封号/停广告
```

APP 上报的数据不能作为奖励或处罚的最终依据。广告奖励必须依赖服务端广告会话、provider 回调或签名校验；风控评分只能影响广告请求策略或进入人工审核队列。

## 5. 最小改造方案

### 5.1 先建立指标快照

新增日级或小时级指标表，至少包含：

```text
id
scope_type        # agent / game
scope_id
window_start
window_end
pay_rate
retain_1
ctr
flow_growth
device_repeat
source             # kwai_report / internal_event / manual
source_snapshot   # 原始文件或接口批次引用
created_at
```

每个主体/游戏/时间窗口只能有一个明确版本的指标快照，手工录入也要保留原始值、操作者和批次。

### 5.2 版本化评分规则

新增规则配置或代码版本字段：

```text
model_name = kwai_union_risk_guard
model_version = v1-revised
weights
thresholds
input_unit_definition
effective_from
```

每条 `RiskRecord` 应保存 `model_version`、五项输入快照、总分、分项分数、预警等级和建议，不要只保存最终 `risk_score`。

### 5.3 改成纯函数并补测试

建议接口：

```python
score = calculate_risk(metrics, rule_version="v1-revised")
```

必须测试：边界值、缺失值、非法单位、单项上限、总分范围、样例数据、重复计算和规则版本变更。模型在接入前至少要用历史样本验证误报率、漏报率和分层稳定性。

### 5.4 后台只读预警，动作需要人工确认

第一阶段只增加：

- 风险分数和等级列表；
- 五项输入和分项得分详情；
- 数据来源、窗口和模型版本；
- 忽略/确认/复核记录；
- 预警导出和审计日志。

“暂停首充、缩减流量、限制广告”应作为带权限和审计的人工操作，等回测证明可靠后再考虑半自动化。

## 6. 是否现在接入

| 目标 | 结论 |
|---|---|
| 直接运行 TXT 脚本 | 不适合，文件本身不是可执行脚本 |
| 直接接入用户 APP 广告请求 | 不适合，缺少广告会话和 provider 验证 |
| 直接自动封号/停投/改充值策略 | 不适合，公式未校准且没有审批链 |
| 作为后台离线预警原型 | 可以，先修正公式并手工导入指标 |
| 作为项目正式风控模块 | 有条件适合，完成数据、模型、审计和回测改造后接入 |

## 7. 最终建议

当前建议为：**暂不直接介入生产；保留为候选规则，先做离线评估和数据接入设计。**

接入前必须完成：

1. 向业务方确认五项指标的精确定义、单位、统计窗口和风险方向。
2. 修复设备重复项、留存项和所有输入校验。
3. 获取快手官方数据来源或明确合规的报表导入方式；当前文件声明自身不对接官方接口。
4. 建立主体/游戏维度的指标快照和规则版本。
5. 使用历史异常样本进行回测，确认阈值和误报率。
6. 先接入后台预警和人工复核，暂不自动影响用户金币、账号状态或广告奖励。


## 当前后台实现状态

已按上述边界新增独立的“快手风控”后台板块。它支持 operator/superadmin 手动录入五项指标、按 `v1-revised` 修正规则计算、保存版本化历史、按主体/游戏/日期/等级筛选，并展示分项得分、风险等级和整改建议。该板块只提供人工预警，不自动封号、扣金币、暂停广告或改变 APP 广告奖励链路。

接口为 `GET /api/v1/kuaishou-risk`、`POST /api/v1/kuaishou-risk` 和 `GET /api/v1/kuaishou-risk/{assessment_id}`；数据库迁移为 `e924_kuaishou_risk_assessments`。
