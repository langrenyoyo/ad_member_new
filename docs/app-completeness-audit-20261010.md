# APP 完整性复查（2026-10-10）

结论：基础业务已具备集成测试条件，尚不满足全部最新需求，也不足以判定可正式上线。本轮为静态代码审查和已有测试报告核验，未修改业务代码、未调用线上金融接口。

## 优先修复

1. **提现待确认请求可能无法恢复。** `IdiomQuizApp.kt:1569` 要求余额大于零、有可用档位和支付服务可用才允许进入重试入口。若服务端已冻结全部余额但响应丢失，刷新后余额为零，用户无法用持久化的 request_key 确认原申请。档位移除也有相同问题。后台 `payouts.py:169` 已支持先返回原幂等订单；客户端应提供不受新申请条件限制的独立“确认上次提现”入口，并根据返回记录清理本地状态。
2. **明确拒绝可能被保留为待确认提现。** `QuizViewModel.kt:271` 仅首次 400/422 清理键；后台余额不足、次数限制、未绑账户为 409，黑名单为 403。用户一次大额申请被拒后，尝试更小金额会被本地旧金额检查拦截。需要明确业务错误码区分“未创建”与“结果未知”，不能盲目清理所有 409。
3. **广告回调未绑定发起会话。** `QuizViewModel.kt:306` 开始的 SDK 回调在触发时重新取得当前认证凭据，退出后切换账号可能用新账号上报旧广告，并更新新界面的状态。单个 HTTP 请求的 SessionFence 不能覆盖跨回调、轮询和多步骤业务流程。需要在业务开始时捕获会话代次，并在每个回调/轮询校验。此问题不等于已证明后台会给错误账号发奖。
4. **微信事件订阅可能因会话取消永久停止。** `QuizViewModel.kt:44` 的长生命周期 collect 内直接执行可抛 CancellationException 的认证请求。微信登录/设密过程中退出会使请求代次失效，从而终止整个订阅协程；同一个 ViewModel 后续可能不再处理授权事件。需将每次授权处理与长期事件订阅隔离。
5. **微信设密缺少回调丢失恢复。** `passwordAuthorization` 仅在成功、失败、退出时清理，无授权超时或主动取消恢复入口。若 SDK 无回调，isBusy 会一直为 true；进程重建也不恢复该流程。应允许安全取消并重新授权，不持久化明文密码。
