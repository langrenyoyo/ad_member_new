## 已确认的问题

### P1：可信 ECPM 的部署与准入校验没有闭环

- `backend/app/taku_ecpm.py:27` 依赖 `TAKU_ECPM_KEYRING_FILE`。
- `docker-compose.yml` 未透传此变量，也没有专门的 ECPM 密钥文件挂载配置；`.env.example` 缺少相应指引。现有支付宝密钥目录挂载不能自动设置此环境变量。
- `backend/app/member_policy.py:220` 保存策略、`backend/app/main_from_txt.py:2973` 广告准入均未检查可信 ECPM 所需密钥配置。准入只检查普通奖励回调密钥与广告位。
- 临时库复现：无 ECPM keyring、启用可信分段策略，广告请求返回 201；合法普通奖励回调在无法提供可信价格时返回 503。用户可能看完广告后长期等待奖励。
- 建议：补环境变量与密钥文件部署契约，增加策略启用和广告准入的配置预检及后台状态提示；针对实际广告源联调人民币证明，不能以普通回调密钥配置成功代替 ECPM 验证。

### P1：奖励回调与曝光乱序导致标签漏样，人工复核也无法补救

- `backend/app/main_from_txt.py:3034` 附近的曝光接口只接受 issued 状态。
- 奖励回调允许 issued 状态直接结算，结算后不补 impressed_at。
- `backend/app/member_insights.py:41` 拒绝复核无 impressed_at 的广告；`:63` 标签样本也只统计 impressed_at 非空记录。
- 临时库复现：合法服务端回调 200，状态 rewarded、impressed_at 为空、标签样本数为 0；随后曝光补报 409，人工分类复核 409。
- APP `QuizViewModel.kt:505` 的曝光上报失败只记录日志，没有持久化重试，元数据上报也没有持久化补偿。因此网络抖动或回调乱序会影响用户标签及后续固定奖励。
- 建议：展示证据与结算状态解耦；已结算会话允许幂等补报，单独保留证据来源，不能伪造实际曝光时间；为已验证奖励记录定义复核/统计规则；客户端增加同事件 ID 的有界重试及持久化恢复。

### P2：广告自动识别仍未实现

- SDK 采集的是平台、广告源与可能存在的标题候选字段，未保证返回真实应用名称或行业。
- 当前标签来自超级管理员人工复核，尚无 OCR/AI 服务、授权素材采集、置信度或自动识别任务队列。
- 因此“自动识别所看广告并自动打标签”不能标为完成，也不能凭标签推断快手实际核减原因。
- 建议：先收集真实 SDK 字段样本，确认可用素材来源，再实现识别、低置信度人工审核和评估集；异常拦截待明确业务标准。

### P2：生产资金迁移尚缺历史对账与 PostgreSQL 验证

- 钱包、冻结余额及金币流水已改 Numeric(24,6)，资金写入使用 Decimal。
- e932 对每个历史字段独立截断六位小数，并归档原值；未自动检查各行 coin_before + coin == coin_after、会员余额与流水及在途冻结款一致。独立截断不保证历史恒等式仍成立。
- 已验证 SQLite 空库迁移及模型表字段覆盖；这不能证明 PostgreSQL 的存量数据迁移、并发锁、迁移耗时和容器部署通过。
- 旧接口仍通过 float 输出金额以保持兼容，旧报表仍有 Float；不能宣称全链路、全库精度完全统一。
- 建议：上线前在生产副本执行迁移前后对账，输出差异清单并显式处理；保留备份及维护窗口，补 PostgreSQL 并发与恢复验证。

### P2：APP 进程恢复与观测规模仍有边界

- `MemberCenterViewModel.kt:43` 的补贴申请幂等键及内容指纹只在内存中，进程死亡会丢失原请求恢复上下文；表单多处使用 remember，重建后可能丢失输入。后台仍有活动唯一约束，不能据此断言必然重复付款。
- `member_insights.py:228` 设备观测分页仍读取全部活跃 peers，再对当前页逐个扫描，分页不限制整体计算量。`:478` 的 settlement_snapshot 每次广告请求计算标签，即使标签奖励未启用；游戏级锁内的查询会增加串行处理时间。
- 建议：持久化待确认申请键及用户草稿，退出账号清除；观测聚合增加数据库索引与空间/分桶统计，基于实际并发压测再调整锁和标签缓存。
